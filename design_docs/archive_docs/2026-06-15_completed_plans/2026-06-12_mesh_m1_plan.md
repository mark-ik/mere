## Where the mesh lives (resolving brief §12)

New supercrate **`crates/mesh/`**, crate **`mesh`** (plain word, one
concern: the personal→communal compute mesh's wire format, job-board state,
and sync session). Consumers: the `mesh-peer` example bin now; meerkat's P6
compute actor later; the bounty/economy layers (M4+) extend the same op
grammar per the resource brief's `BankingEvent` sketch.

## Design (mirror tessera's proven LogSync lane)

The template is `moothold/src/tessera/` — the shape the two-peer-convergence
suite proved. One store of record, one write path; authoring and receiving
share it.

- **Wire** (`wire.rs`): signed p2panda `Operation<MeshExt>`, the mesh id as
  the *signed addressing extension* (mirroring `TesseraExt`); p2panda 0.6.1
  pins as moothold. Ops:
  - `JobPosted { kind, payload, nonce }` — M1 payloads are inline-small
    (blobs via iroh-blobs arrive with M2's `MeshResource`).
  - `JobClaimed { job: Hash }` — a worker's claim on a posted job.
  - `JobDone { job: Hash, result }` — the claimed job's result.
- **Job kinds (M1)**: `Echo` and `Blake3` — pure, deterministic,
  dependency-free. They prove transport + protocol + state convergence; real
  kinds (embeddings batch, Burn job) arrive with M2's `MeshResource` trait,
  which is exactly one adapter per the brief's milestone 2.
- **State** (`board.rs`): `JobBoard`, a deterministic fold of the op log
  (the `Ledger` pattern): `posted → claimed → done`. **Claim races resolve
  deterministically**: every peer picks the same winner (lowest claim-op
  hash); only the winner's `JobDone` is accepted. Lapse/heartbeat/reassign
  is milestone 3, not here. The fold is a pure function (op slice in, board
  out) so it tests without any networking.
- **Sync** (`sync.rs`): `SyncedMesh` mirroring `SyncedMoot::join(endpoint,
  gossip, store, mesh_id)` — LogSync session over the store, verifying drain
  task, **real `SyncStatus`** (rounds, ops received, last activity; the
  no-placebo rule).
- **Store** (`store.rs` + `log_store.rs`): step 0 probes whether
  `p2panda_store`'s in-memory store satisfies LogSync's trait bounds
  (`LogStore` + `TopicStore`); if yes, M1 rides it behind a small store
  seam. If not (tessera built redb for a reason), mirror tessera's redb
  store + index tables (`OPS_BY_LOG`, `LOG_TOPICS` shapes) — known-good,
  more code. Either way the seam lets M2 swap durability in without touching
  wire/board/sync.
- **Worker** (`worker.rs`): `next_action(&board, me) -> Option<Claim|Execute|Post>`
  as a pure function plus a thin async loop helper; the *host* drives it
  (the peer bin now, the P6 actor later). Owner-priority/preemption is M+
  scheduler work — M1 workers run when asked.
- **The peer bin** (`examples/mesh-peer.rs`): `mesh-peer work` /
  `mesh-peer post <text>`, sharing a mesh id derived from a seed env var,
  printing the board and real sync status. This is the artifact for the
  done-condition's two-machine run.

## Tests (in dependency order)

1. Wire round-trip + signature verification (mirror tessera's `wire` tests).
2. Board fold: lifecycle, idempotent re-fold, **claim-race determinism**
   (two claims, both orders, same winner), reject `JobDone` from
   non-winners.
3. Two-peer convergence: dev-dep on `transport` (tessera's pattern — the
   lib takes raw `Endpoint`/`Gossip`; the test builds two real p2panda-net
   peers in-process), post on A, claim+execute on B, result lands on A.
4. The two-*machine* run is Mark's verification (laptop posts, workstation
   works), via `mesh-peer` — the milestone's literal done-condition.

## Done conditions

- `cargo test -p mesh` green covering 1-3 above.
- `mesh-peer` round-trips a job between two in-process peers on one machine
  (same binary, two processes) as the rehearsal for the two-machine run.
- The workspace gains `crates/mesh/` + the pin entry; the cross-repo smoke
  stays green.
- No meerkat changes, no economy types, no blob fetching (those are M2/M3/M4
  and the plan says so rather than half-building them).

## Out of scope (named, per the brief's staging)

M2 `MeshResource` + first real adapter; M3 idle routing, heartbeat/reassign,
and redundant validation (the BOINC-shaped queue); M4+ bounty grammar/escrow
(the economy). Kith capability grants (ring 2) — M1 is own-devices only;
every peer with the mesh id is trusted (the personal ring's definition).

## Progress

- **2026-06-12** — Plan written; lane chosen explicitly as parallel-safe
  while genet-layout (viewport work) and meerkat (window-composition
  reshape) churn. Design mirrors tessera's LogSync lane one-for-one (store /
  wire / synced-session / deterministic fold), with the store-probe as step
  0 and the claim-race determinism rule as M1's one novel decision.
- **2026-06-12** — **The pure core landed: `crates/mesh/mesh` with 11 tests
  green.** `wire.rs` (signed `Operation<MeshExt>`, the tessera mirror:
  round-trip, verify, cross-mesh-replay tamper test, p2panda
  validator-compatibility test), `board.rs` (the order-independent fold;
  claim-race winner = lowest claim-op hash, proven identical across fold
  orders; non-winner `JobDone` rejected; foreign-mesh ops skipped),
  `worker.rs` (pure `next_action`: execute-what-you-won before claiming;
  losers idle; `Echo`/`Blake3` executors, deterministic by test). Workspace
  member + pin added. Two API spellings differed from the tessera template's
  era (`Hash::digest` not `new`; `VerifyingKey::as_bytes` not `to_bytes`) —
  caught by compile, no design impact. **Step 0 resolved**: p2panda-store
  0.6.1 ships SQLite impls of all store traits with in-memory default
  (`SqliteStoreBuilder`), so the sync slice rides it — no custom redb store
  needed (tessera built redb because its ops already lived there; mesh has
  no prior store). **Next slice**: `sync.rs` (`SyncedMesh` over the sqlite
  store, the `SyncedMoot` mirror) + the two-peer convergence test (dev-dep
  transport) + the `mesh-peer` bin for the two-machine done-condition.
- **2026-06-12** — **The sync slice landed: 17 tests green, in-process
  rehearsal ran the milestone round-trip end to end.** `store.rs`
  (`MeshStore` over p2panda-store's `SqliteStore`: one transactional write
  path that persists the op row *and* its topic→author/log sync index
  together; reads ride the pool; in-memory and file-URL constructors, with
  a reopen test) and `sync.rs` (`SyncedMesh`, the `SyncedMoot` mirror, plus
  the two mesh-specific additions: `author()` — sign at the device's next
  seq/backlink, persist, push onto the live gossip lane — and `board()`;
  real `SyncStatus` + the settle-watch `resync`). Two-peer tests cover both
  lanes: the live round-trip (post on A, claim+execute on B via
  `next_action`, result lands on A) and the RBSR catch-up (late joiner
  converges on a pre-existing log). `examples/mesh-peer.rs` (`work` /
  `post <text>`, `MESH_SPACE`/`MESH_SEED` env, ticket on stdout + pasteable
  peer tickets on stdin) ran the same-machine rehearsal: two processes,
  result landed, exit 0. Cross-repo smoke green; moothold unaffected by the
  sqlite feature unification. Findings worth keeping: p2panda's in-memory
  sqlite needs `max_connections(1)` (each pooled connection is its own empty
  database); store writes need explicit `begin`/`commit` permits; a one-way
  ticket bootstrap (only the poster holding the worker's ticket) converges
  but waits for a reconciliation round (~45-50 s observed) — pasting tickets
  **both ways** engages the live lane and converges in seconds, so do that
  on the two-machine run. **Remaining for M1**: the literal two-machine run
  (laptop posts, workstation works) — Mark's verification, via `cargo run
  -p mesh --example mesh-peer`.
- **2026-06-12** — **The first real two-machine attempt (laptop ↔ Fedora
  ThinkPad) stalled and found a transport bug, now fixed.** Both peers'
  setup was correct (spaces matched, identities distinct; both tickets
  pasted), but `transport::endpoint_addr` built tickets from the endpoint's
  *bound* sockets, rewriting the wildcard bind to **loopback** — its own doc
  called it "the test pattern". Each machine therefore told the other "dial
  me at 127.0.0.1": the same-machine rehearsal worked by construction, and
  cross-machine could never connect (no relay or discovery as fallback).
  Fix in `transport` (the engine, not the bin): `endpoint_addr` now starts
  from `iroh::Endpoint::addr()` — the machine's real interface candidates,
  with a bounded (≤1 s) wait for iroh's interface discovery — and keeps the
  loopback rewrite as an additional candidate so in-process pairs still
  work on an interface-less host. Verified: transport 28 tests, mesh 17,
  moothold's two tessera convergence suites all green; the probe ticket now
  carries the Wi-Fi address; same-machine rehearsal still exits 0. The
  `mesh-peer` bin also prints an `addrs :` line so a stalled run can be
  eyeballed (both machines should show same-subnet candidates). The
  two-machine run needs the fix pulled on the ThinkPad (fresh tickets, both
  ways) — still Mark's verification.
