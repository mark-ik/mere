     - [`mere_docs/implementation_strategy/2026-05-25_netfetcher_plan.md`](mere_docs/implementation_strategy/2026-05-25_netfetcher_plan.md) — plan for **`netfetcher`**: a standalone crate + repo that is Servo's `net` *made portable* — the WHATWG Fetch algorithm + CORS / cookie jar / HTTP cache / redirects / HSTS / mixed-content / CSP-hook / content-encoding, lifted off Servo's `ipc-channel` / resource-thread / constellation coupling and exposed as a directly-callable async **library** (`fetch(request, &FetchContext) -> Response`), plus an HTTP/3 (quinn/h3) lane and a modern rustls stack.      - [`mere_docs/implementation_strategy/2026-05-27_verso_adoption_plan.md`](mere_docs/implementation_strategy/2026-05-27_verso_adoption_plan.md) — plan sequencing **verso adoption**, which absorbs route 2 (the custom child-hosting tiling widget) from the [between-tiles layout seam](mere_docs/technical_architecture/2026-05-26_between_tiles_layout_seam.md). Central finding from reading the two verso crates against the live host: **`verso-core`** (portable surface-lifecycle bookkeeping — Present/Retire/Focus, placement plans, deferred-retry backlog) and **`tile-state`** (within-tile history + document cache + `SurfaceProducer` tiles) are both keyed on **substrate-era `NodeKey`/`PaneId`**, and their machinery pays rent for **live + external** surfaces (scrying webviews, navigated tiles), **not** the static in-scene workbench tiles that route 1 renders fine. Phases: **P0** reshape verso keys `NodeKey`/`PaneId` → forme tile-id (spine §14.3, the prerequisite, portable + unit-testable); **P1** the `WorkbenchTiling` Masonry widget (route 2 proper — `layout()` runs `platen::layout_plan` at the real size, `place_child` + clip, Xilem View/Splice mirroring `zstack`; masonry-`TestHarness` placement-rect + hit-routing tests, headless); **P2** live document tiles (within-tile history/cache); **P3** external-surface tiles (scrying) where verso lifecycle + the Xilem `composite_external_layers` driver edit + the [DOM-bridge observable channel](../../serval/docs/2026-05-26_scrying_dom_bridge.md) converge. Sequencing decision posed: **A** realization-first (P0→P1 now, prove the widget against the static workbench) vs **B** consumer-first (P0 then jump to P3/scrying where verso pays full rent, backfill P1/P2). Recommends **B** (don't build realization machinery ahead of a consumer; route 1 holds the workbench meanwhile).

## Working principles

- **Printing-press metaphor** organizes the data flow in two threads:
  - *Per-node content production*: engines (Wry, Serval, Nematic) → **inker** (selects/orchestrates engine + handles routing) → per-node engine output.
