## The one idea

The event-DAG is authoritative (content); every view is a projection of it (experience). Today murm achieves "convergence" by one peer pushing a full snapshot over a stream and the other ingesting it. That is not sync; it is a manual copy. p2panda-net already ships the real thing: gossip for membership/liveness per topic, and RBSR log-sync for catch-up. Wiring it makes a space's operations replicate automatically, and the materialized view falls out as a projection.

## What blocks it today (the load-bearing finding)

p2panda-core is a **per-author append-only log**, not a multi-parent DAG. LogSync replicates those logs: it reconciles, per `(author, log)`, the operations identified by `seq_num` + `backlink`. The spike sets `seq_num = 0` and `backlink = None` on every murm operation (causality rides entirely in the app-level `CabalExt.parents`). **That means there is no real per-author log for LogSync to sync yet.** So the first phase is not transport wiring; it is giving each author a real log.

This is the "per-author-log-plus-refs" reframe the spike's S2 chose, now made concrete: the per-author log (`seq_num`/`backlink`) is the **sync unit**; the multi-parent `parents` set is the **causal-DAG view** reconstructed app-side on top of it. Both are needed; they answer different questions (replicate vs order).

## Phases (done-conditions, not dates)

### Phase 1 — Real per-author logs

- Each `(author, space)` maintains a log: `seq_num` increments per the author's operations in that space; `backlink` = hash of that author's previous operation in the space.
- `CabalExt.parents` stays as the cross-author causal-ref set (the DAG view), layered on top.
- The murm `CableEngine`/stores track per-author heads so authoring sets `seq_num`/`backlink` correctly, and ingest validates them.
- The operation id becomes `Header::hash()` (the signed-header hash), aligning `PostId`, `backlink`, and the LogSync/p2panda log identity on one value (replacing the old BLAKE3-of-wire id).
- **Done when:** a peer's operations form a verifiable single-author chain, and the existing murmuring/murm tests still pass with real `seq_num`/`backlink`. **✅ Done 2026-06-02** (see Progress).

### Phase 2 — Space ↔ topic mapping + subscription

- Map a Mere space to a p2panda-net `Topic`. First cut: `topic = space_id` (the cabal id / cluster-path-derived id we already compute). Open question below on per-channel vs per-space granularity.
- Add a `subscribe(space)` path on the transport (or a thin sync layer above it) that joins the topic; gossip then surfaces neighbours and sync initiates on `NeighbourUp` (discovery-driven, per Probe 1).
- **Realized via gossip (2026-06-02).** `P2pandaTransport::builder().gossip()` spawns the `Gossip` overlay; `subscribe(topic) -> GossipHandle` joins the space topic (a handle to `publish` ops to / receive ops from peers in the space); `set_topics(peer, …)` tags a peer's topic for explicit bootstrap (discovery does this confidentially in production). `Topic = p2panda_core::Topic::from(space_id)`.
- **Done when:** two peers subscribed to the same space converge. **✅ Done 2026-06-02** — a real two-peer test (`gossip_propagates_ops_between_subscribed_peers`, transport 27 green) shows bytes Alice broadcasts reach Bob over the overlay (~2.4s). It uses explicit bootstrap (`add_peer` + `set_topics`); the "without explicit `add_peer`" production path rides the already-wired discovery (multi-host / timing-dependent to test single-machine, same caveat as discovery).

### Phase 3 — Ingest → projection

- Wire the synced-operation stream into the projection sink: today `CableEngine::ingest_post` (which already verifies signature + the self-describing `cabal_id`, and is idempotent via content addressing); later the moot graph-view CRDT.
- **Realized at the murm level via gossip (2026-06-02).** `Murm<P2pandaTransport>::subscribe_cabal(cabal_key) -> SyncedCabal` opens the cabal, joins its gossip topic, and spawns a background task that ingests posts peers broadcast (`decode_post` → `ingest_post`). `SyncedCabal::send_text` stores locally *and* broadcasts. It is a concrete `impl Murm<P2pandaTransport>` (the generic `Murm<T>` core is untouched).
- **Done when:** two peers subscribed to the same cabal converge. **✅ Done 2026-06-02** — `two_murm_peers_converge_over_gossip` (murm 14 green): Alice authors via `SyncedCabal`, Bob's background ingest task lands it, Bob's `history` converges (~2.7s, explicit bootstrap). This supersedes the manual `push_cabal_to_peer` / `accept_*` snapshot dance for *online* peers (Phase 4 can retire it once offline catch-up via LogSync is also in place).

### Phase 4 — Retire explicit push/accept

- Remove the spike's snapshot push/accept path from murm once subscription-driven sync covers it. Keep `add_peer` only as a bootstrap hint (seed a peer when discovery can't find one).
- **Done when:** the murm cross-peer tests pass over subscription sync, and the bespoke push/accept code is deleted (no parallel system, per DOC_POLICY §3). **✅ Done 2026-06-02** — deleted `push_cabal_to_peer` / `accept_cable_connection` / `handle_cable_stream`, the LEB128 varint helpers, the now-dead `all_posts` (engine + store), and the two snapshot tests; `add_peer` stays as the bootstrap hint. transport 27 + murmuring 73 + murm 13 green; convergence now rides only the gossip + LogSync lanes.

### Phase 5 — Live gossip for low latency

- Use gossip broadcast for new-operation fan-out (low latency) alongside LogSync for catch-up (a peer that was offline). Sync is the floor; gossip is the fast path.
- **Done when:** a new operation appears on subscribed peers promptly without waiting for a full sync round.

## Findings

- **p2panda-net sync model (read from source 2026-06-02):** `sync::LogSync` + the sync manager run a gossip overlay per topic (topics are "mixed" with a constant before gossip to avoid cross-use collisions); `GossipEvent::{Joined, NeighbourUp, NeighbourDown}` drive `InitiateSync`/`EndSync`. So subscribing to a topic is the entire public surface; initiation is automatic. `SyncHandle::initiate_session` is `#[cfg(test)]`, confirming sync is not manually driven (Probe 1).
- **RBSR is already here.** Per the substrate brief §5, iroh-docs/p2panda-sync already does range-based set reconciliation, so there is no efficiency reason to reach for Willow at the sync layer; Willow is for the data model + meadowcap, which we are already owning natively (cluster-path caps).
- **Our operations are sync-ready except for the log.** Post-spike, murm posts are real p2panda operations (BLAKE3/CBOR/Ed25519), so the only gap to native sync is Phase 1 (the per-author log), which is also the thing that makes p2panda-blobs/eidetic and the moot graph-view replicate the same way.
- **The operation id had to become the signed-header hash (Phase 1, while implementing).** p2panda's `validate_backlink` checks `backlink == past_header.hash()`, so a valid log requires `backlink` — and therefore the operation id — to be `Header::hash()`, not the old BLAKE3-of-CBOR-wire id. Aligning `PostId = Header::hash()` unifies content-address, backlink, and sync identity on one value; it was a required part of Phase 1, not optional. Proven by a test that runs p2panda's own `validate_header` + `validate_backlink` on our two-op chain.
- **Gossip is the tractable sync mechanism; LogSync needs store-trait adoption (Phase 2, while implementing).** `Gossip` (ephemeral broadcast) gives *online* convergence with no extra machinery: publish encoded ops to a topic, receive + ingest peers' ops (proven by a real two-peer transport test). `LogSync` (RBSR, the *offline catch-up* guarantee) requires the store to implement `p2panda_store::{LogStore, TopicStore}` (its builder is `Builder<S: LogStore<Operation<E>,…> + TopicStore<…>>`), which our `InMemoryCabalStore` does not — adopting p2panda-store is a real sub-project. **Re-sequencing:** the plan assumed LogSync was Phase 2's mechanism; in practice gossip is the *first* lane (live convergence, done now) and LogSync is the heavier follow-on (offline catch-up, deferred behind p2panda-store adoption). Phase 5 ("live gossip") is therefore the first sync lane, not the last.
- **redb backs the LogSync store traits — Path B proven, and two real peers catch up over it (2026-06-02).** p2panda's storage layer is trait-based by design (`SqliteStore` is only the reference impl); `LogStore` + `OperationStore` + `TopicStore` map cleanly onto redb's ordered-key + range-scan + transaction model. A probe implements all three over redb; not only does `LogSync::builder(redb_store, …).spawn()` accept it, **two real p2panda-net nodes on loopback run an actual RBSR catch-up over the redb store** — Alice's store holds a 3-op per-author log associated with a topic, Bob starts empty, and after the overlay forms Bob receives and persists all three of Alice's ops (stable across repeated runs). So the offline-catch-up lane stays **pure-Rust** (no SQLite/C dependency), reusing the redb dep we already have. The earlier "against the grain" worry was wrong: the traits are storage-agnostic, and redb is exactly the shape they want.
- **LogSync joins gossip on a *derived* overlay topic, not the raw sync topic (2026-06-02, while wiring the two-peer probe).** The sync manager mixes each sync topic with a private constant — `gossip_overlay_topic = BLAKE3(sync_topic ++ GOSSIP_TOPIC_MIX_VALUE)` (its `derive_topic`) — to avoid collisions between the membership overlay and any application gossip on the same topic. Consequence for explicit bootstrap: `address_book.set_topics(peer, …)` must tag peers with the **derived** topic for the LogSync overlay to form and auto-initiate; tagging the raw topic silently forms no neighbour link (the probe got zero sync events until this was fixed). `stream(sync_topic, …)` and `TopicStore::associate(sync_topic, …)` still take the **raw** topic — only the address-book peer-tagging needs the derived one. Both `derive_topic` and the constant are private in p2panda-net 0.6.1, so the probe replicates them; if we wire this for real, either upstream a public helper or keep the replicated constant under test.

## Open questions

- **Log granularity.** One log per `(author, space)`, or per `(author, space, channel)`? Per-space is simpler and matches the cabal id we already sign in; per-channel allows finer sync but multiplies logs. Lean per-space for v1.
- **DAG view over per-author logs.** How the multi-parent `parents` reconcile with the linear per-author logs at the projection layer (ordering, head-tracking). The data-scheme `SecretBundle`/timestamp ordering and our `parents` both exist; pick one ordering authority for the view.
- **Eidetic / blobs.** Large payloads sync as content-addressed blobs via iroh-blobs (already in the transport), not as operations. Confirm the split: operations carry refs (hashes), blobs carry bytes, cheesecloth pins serve the blobs.
- **Moothold federation.** At t3, federation = cross-moot topic subscription + the reciprocity ledger deciding which spaces a moot replicates for another. This plan is the t1/t2 substrate; the t3 policy rides on it.
- **Pruning / compaction.** p2panda has prune flags (`PruneFlag` extension); when do we drop old log prefixes vs keep for lapse-and-revive? Couples to the moot brief's durability story.
